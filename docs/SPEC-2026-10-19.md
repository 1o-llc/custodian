I want to extend Custodian's architecture with a very important distinction: **bounded and unbounded modes for repository understanding, change planning, and specification-driven program transformations.**

Please inspect the current Custodian implementation and the relevant existing crates before deciding how to integrate this. Preserve working architecture, repository boundaries, and existing capabilities. Reuse my published primitives rather than creating competing implementations.

## 1. The original reason Custodian exists

This must be explained prominently in Custodian's README.

I originally created Custodian because coding agents, particularly Claude, would start substantial tasks without fully understanding the repository, its use sites, dependencies, feature configurations, and potential consequences.

Then, partway through execution, the agent would encounter a question it couldn't answer or discover that it needed a decision from me.

This creates planning debt: the user believes the agent is progressing toward completion, but the work is actually contingent on unresolved questions that could have been discovered beforehand.

**Custodian's fundamental purpose is to make agents understand the codebase, determine the affected scope, and identify meaningful questions before committing to execution.**

Its original identity is closer to a repository records custodian than a general-purpose maintenance runner.

Maintenance, construction, and transformation capabilities should extend that purpose, not replace it.

The desired behavior is:

- Investigate the codebase before committing to changes.
- Discover relevant definitions, references, use sites, dependencies, feature constraints, and architectural relationships.
- Separate questions answerable from repository evidence from decisions that genuinely require the user.
- Ask essential questions early and together, rather than repeatedly interrupting execution.
- Avoid asking the user questions that can be answered deterministically using the available tools.
- Make progress independently when the requirements and authorization are sufficient.
- Preserve the distinction between a proposed change, an authorized change, and a completed, verified change.

## 2. Introduce bounded and unbounded operation modes

These should be explicit operating modes with shared underlying repository intelligence.

### Bounded mode — precise, constrained changes

The agent specifies a concrete operation and its permitted scope.

Examples:

- Modify this struct.
- Add this field.
- Add an enum variant.
- Generate a constructor.
- Add a method with a specified signature.
- Update an implementation.
- Identify and update impacted call sites.
- Modify a feature declaration.
- Perform a constrained refactoring.

Custodian should:

1. Resolve the exact target using indexed repository information.
2. Identify its definitions, references, use sites, dependent types, and relevant packages.
3. Determine the affected scope, including feature configurations.
4. Produce an impact and cost assessment before execution.
5. Validate the requested transformation and its preconditions.
6. Determine whether the operation is authorized within its declared boundaries.
7. Apply the change through the appropriate existing transformation tooling.
8. Run appropriate targeted validation.
9. Produce structured diagnostics and an execution receipt.

Bounded mode should not silently expand the permitted modification scope.

If the requested change requires modifying additional packages, files, or interfaces outside its authorization, Custodian should report that requirement and request a scope expansion where necessary.

Exploratory reads may be broader than authorized writes, subject to their own access restrictions.

### Unbounded mode — intent-driven planning and discovery

In unbounded mode, the agent receives a higher-level objective rather than a fully specified transformation.

Examples:

- Implement a new subsystem.
- Add support for a new capability.
- Design a feature-management workflow.
- Determine what would be required to change the repository's execution architecture.
- Identify everything needed to implement a requested behavior across multiple packages.

Unbounded does not mean unrestricted filesystem access or unlimited authority.

It means **the scope of the proposed work is initially unknown and must be discovered**.

Custodian should:

1. Interpret the requested outcome.
2. Investigate relevant repository structure and architectural relationships.
3. Identify existing crates and functionality that can be reused.
4. Determine what new modules, types, functions, libraries, or interfaces may be necessary.
5. Identify the likely affected packages, use sites, features, and tests.
6. Estimate costs, risks, and implementation complexity.
7. Detect unresolved requirements and genuinely necessary user decisions.
8. Present a coherent proposed execution plan.
9. Convert approved portions of that plan into bounded, executable operations.

The key distinction is:

**Unbounded mode discovers and proposes the work. Bounded mode authorizes and executes precisely defined work.**

An unbounded planning session must not automatically grant unrestricted write access.

Also, do not impose an arbitrary requirement that every task must produce three alternative designs. Generate alternatives when there are meaningful architectural tradeoffs, and explain their relative costs.

## 3. Introduce structured change-impact and cost analysis

Custodian should expose a first-class mechanism for answering questions such as:

- What happens if I add a field to this struct?
- Which constructors and struct literals will be affected?
- Which traits or implementations need modification?
- Which packages depend on this type?
- Which features influence this code?
- Which tests need to be updated or executed?
- Does the change affect serialization or public API compatibility?
- Does it affect concurrency, memory layout, allocation, or runtime behavior?
- What is the estimated implementation and verification cost?
- Can the change be completed within the currently permitted scope?

Costs should be multidimensional rather than a single unexplained number.

Consider exposing:

- Number of directly affected definitions.
- Number of known use sites.
- Number of potentially affected files and packages.
- Dependency fan-out.
- Feature combinations affected.
- Likely API compatibility impact.
- Estimated compilation and test workload.
- Runtime or memory implications when reasonably derivable.
- Confidence and uncertainty in each estimate.

Distinguish deterministic measurements from heuristics and unknowns.

For example, adding a field may have measurable impacts on references and struct initialization, while its actual runtime cost may depend on alignment, representation, use patterns, and optimization.

Do not invent precise performance estimates when the necessary evidence is unavailable.

The agent should be able to query this analysis before deciding whether to proceed.

## 4. Extend SimpleImpl through reusable transformation contracts

Inspect the actual SimpleImpl and SimpleImpl Derive implementations before modifying them.

Determine how their existing functionality can support declarative construction of:

- Structs and fields.
- Enums and variants.
- Constructors.
- Methods and associated functions.
- Trait implementations.
- Derives and implementation boilerplate.
- Function signatures.
- Constrained transformations of existing Rust items.

The goal is to let an agent specify what it wants changed without always generating arbitrary source-code replacements.

For example, a conceptual operation might express:

- Target: `JobRecord`
- Operation: Add field
- Field: `digest`
- Type: `Digest`
- Required compatibility: Preserve existing constructors where possible
- Allowed modification scope: Selected crate
- Validate affected call sites: Yes

This is conceptual, not a prescribed syntax.

Identify which transformations SimpleImpl can actually perform today and which require extensions.

For complex function internals, do not assume that declarative specifications inherently guarantee correctness. Investigate whether a controlled operation vocabulary, syntax-aware transformations, and explicit postconditions would be appropriate.

Avoid turning SimpleImpl into an unrestricted code-generation framework if that conflicts with its existing purpose.

## 5. Use Custodian specification files as the central contract

The agentic kit should be able to create specifications within Custodian's designated specification directory.

Specifications may describe:

- The requested objective.
- Bounded or unbounded operating mode.
- Target definitions or packages.
- Proposed operations.
- Authorized read and write scope.
- Relevant feature requirements.
- Required validations.
- Expected outcomes and postconditions.
- Unresolved decisions.
- Impact estimates and execution evidence.

Examine the possibility of reusing the existing 1o language infrastructure for parsing, diagnostics, semantic validation, and editor support.

Keep shared specification validation available independently of the language-server process.

Investigate using Stable Digest to identify exact specification content and bind execution receipts to the specification version used.

Do not treat a valid hash or syntactically correct specification as authorization to execute it.

## 6. Support explicit architectural linkage records and comments

This is another important capability.

I want Custodian to discover not only where code is used, but **why certain code and libraries were used**.

Investigate a structured, discoverable way to represent architectural relationships, potentially through compatible source comments, metadata, attributes, or specification records.

Examples of the information I want to preserve:

- This module uses another crate because it owns a specific responsibility.
- This implementation depends on a particular invariant.
- These two types are connected for a particular architectural reason.
- This feature exists to satisfy a compatibility requirement.
- This code must remain synchronized with another implementation.
- This function must not be modified without considering another subsystem.
- This dependency must not be replaced casually because its semantics are required.

These records should be searchable and linkable to concrete repository symbols and paths.

Use real resolved references rather than relying solely on informal natural-language comments.

Architectural notes should support provenance, invalidation, and stale-reference detection. Comments and annotations must not automatically be trusted as authoritative without validation.

The objective is for agents to recover both **structural relationships and design intent**.

## 8. Preserve the original agent-efficiency objective

Custodian should reduce unnecessary repository rediscovery, repeated shell commands, token expenditure, and mid-task human interruptions.

It should not become a complicated intermediary that costs more effort than the operations it replaces.

Provide compact, machine-readable output suitable for coding agents.

Support targeted queries and selective expansion of detailed results.

Track useful efficiency metrics where practical, such as:

- Repository discovery operations avoided.
- Repeated file reads avoided.
- Tool calls required.
- Time spent performing preflight analysis.
- Questions identified before execution.
- Blockers discovered after execution began.
- Successful job completion rates.
- Token consumption when measurable.

The goal is improved reliability and more independent task completion, not simply fewer tokens.

Update Custodian's README to explain its original motivation and primary purpose.

Make it clear that Custodian began as a solution to a recurring failure mode in coding agents: starting work before adequately understanding the repository and discovering necessary user decisions too late.

Describe it as a repository-awareness and pre-execution intelligence system first.

**The desired outcome is an agent that understands what a task entails before starting it, can explain the cost and impact, asks necessary questions early, and then completes authorized work without repeatedly returning to the user for information that was discoverable beforehand.**

## Additional requirement: Context switching, cognitive load, and unfinished-work accumulation

There is another fundamental reason I created Custodian that needs to be clearly documented in the README and reflected in the architecture.

**I am trying to reduce the cognitive burden of managing multiple coding agents and the accumulation of partially completed work.**

When I begin a substantial task with Claude, I often invest considerable time and attention explaining the problem, the architecture, the requirements, the constraints, and what I want the completed result to look like.

I deliberate deeply because I want the agent to understand the problem sufficiently to carry it through to completion.

Once the agent indicates that it understands the task and will execute it, I mentally hand off responsibility for that work. I may then switch to another agent, another repository, or another complex problem.

The difficulty arises when the original agent subsequently stops and asks questions that could have been discovered or resolved before execution.

By that point, my attention has moved elsewhere.

Now I have to reconstruct the previous task's context, remember the architectural decisions, understand the current state of its implementation, and determine what the agent is asking.

When multiple agents do this across different projects, I accumulate several partially completed tasks that I believed were being handled.

This creates a significant amount of cognitive overhead.

I cannot indefinitely maintain the full context of numerous complicated engineering problems simultaneously, especially when those problems have already been extensively discussed and delegated.

**The agent must respect the cognitive investment made during the original task discussion.**

The objective is not to prevent legitimate questions or eliminate human oversight. It is to prevent avoidable interruptions and unnecessary context reconstruction.

### Required architectural behavior

**1. Front-load understanding**

Before committing to execution, Custodian should help the agent examine the repository, determine dependencies and affected scope, identify uncertainty, and resolve the important questions.

The agent should not claim that it can complete a task when significant, discoverable requirements remain unresolved.

**2. Preserve task context as a durable record**

A task should have a persistent, structured specification containing its objective, constraints, decisions, assumptions, relevant repository evidence, implementation plan, progress, and completion criteria.

This information should survive agent changes, conversation compaction, context-window exhaustion, and interrupted execution.

The agent should be able to reconstruct the task from these records without requiring the user to repeat the original discussion.

**3. Preserve decisions and their rationale**

When I explain why something should be implemented in a particular way, that reasoning should be captured alongside the decision.

A new agent should be able to discover not only what was decided, but why.

Use structured architectural linkage records where appropriate.

**4. Distinguish active execution from blocked or unfinished work**

Custodian should maintain accurate task states.

An agent must not imply that a task is complete, or progressing autonomously, when it is actually blocked, paused, awaiting authorization, or partially implemented.

The system should distinguish proposed, ready, running, blocked, paused, verifying, completed, and failed states where appropriate.

Completion should require evidence that the specified acceptance criteria have been satisfied.

**5. Make context handoffs inexpensive**

When an agent is replaced or its context is compacted, it should be able to retrieve a concise, accurate handoff containing:

- The original objective and acceptance criteria.
- Important architectural decisions and their rationale.
- Work already completed and verified.
- Work remaining.
- Known blockers and unresolved questions.
- Relevant paths, symbols, features, and dependencies.
- The exact next actionable step.

This handoff should be generated from persisted task records and execution evidence, not solely from a language model's recollection.

**6. Minimize unnecessary human re-engagement**

If the agent encounters uncertainty, it should first consult Custodian's repository records, specifications, prior decisions, and available tooling.

Only genuinely unresolved decisions should require human input.

When several decisions are necessary, group them coherently before execution where practical, rather than interrupting repeatedly.

A new agent should not ask questions that the user already answered in another session when those answers are recorded and still applicable.

**7. Prevent hidden unfinished-work accumulation**

Custodian should make it easy to identify which tasks are truly completed, which are still active, and which have stalled.

It should be possible to inspect outstanding work across agents without reopening every conversation and reconstructing the context manually.

This is especially important when multiple agents are simultaneously working on different repositories or subsystems.

### Core design principle

**The user should not have to serve as the persistent memory, task coordinator, or recovery mechanism for the agents.**

When a user has thoroughly explained a problem and delegated its execution, the system should preserve that understanding, manage the work transparently, and minimize unnecessary demands on the user's attention.

A context swap should not mean starting over.

A conversation ending should not mean losing architectural decisions.

A partially completed task should not masquerade as a completed one.

And the user should not repeatedly have to reconstruct problems they have already spent significant effort explaining.

### README requirement

Explain that Custodian originated from two closely related problems:

1. Coding agents beginning tasks without sufficiently understanding repository structure, use sites, dependencies, and the decisions required for completion.
2. The cognitive cost of context switching between agents and projects when unfinished work, late questions, and lost task context force the user to repeatedly reconstruct previously delegated problems.

**Custodian exists to transfer more of that responsibility from the human operator into durable, inspectable, repository-aware software.**

The goal is not merely to make agents faster.

It is to make them more prepared, more accountable, easier to hand off between, and less cognitively expensive to supervise.

This motivation should remain central as Custodian expands into bounded and unbounded operations, specification-driven transformations, impact analysis, and maintenance tooling.

Preserve all previous implementation instructions and architectural requirements. Treat this as an additional foundational requirement, not a replacement for the existing design.
