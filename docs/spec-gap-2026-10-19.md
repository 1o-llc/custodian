## Decisions

Each decision as James would make it, one line each, made while building and not asked.

- (a) One same-search key, the kit's: the spec hash (`custodian_kit::runs::spec_hash`) and klepto's fingerprint (`code_digest`). custodian's own digest of spec + option word + index key becomes a lookup over that key; the option word moves into the spec (a bundle's filters are `ReadingSpec.bundle`), so it is part of the one hash.
- (b) The hook's env keys come from the maintenance registry's `reads_env` marks: the reach reading lists the env keys its reached items read (rows `reach-env`), no new source.
- (c) A code-changing job step (`apply`, `annotate`, `transform`) runs through code_passenger's `transform` line; CUST0024 is raised only for a kind code_passenger has no line for.
- The modes (James, 11:2xZ): BOUNDED is strict, the agent writes no code; it submits change specs, custodian generates and places the code through code_passenger and simple_impl and keeps a transform receipt per applied spec. At `job close` every line the job touched (the open and close counts) must be covered by a transform receipt of the job; any line not covered refuses the close (CUST0031), the result is `rejected`, the lines are listed by file:line. With the pre-edit hook enabled a bounded job refuses a hand edit before it happens. UNBOUNDED is help: readings, plan, impact and cost, the decisions list and reuse by digest are all there, the agent writes code itself, nothing is refused, and the closing receipt still records what ran and the lines touched. `mode` is a field of the job document, its default `job_mode` in `config/custodian.toml` (unbounded when unset); `job start --mode`; `agent brief` says the mode first.
- A test is code too: in a bounded job a test file is written through the `add_test` operation, never by hand.
- `target_known` and `outcome_known` (James, 11:1xZ) are facts derived for a job, not modes. `target_known`: the job's target resolves to a route or an item through the index. `outcome_known`: the job declares its verification up front (`job start --verify LINE`, the job document's `verify`: `test:<name>`, `reading:<spec>` that must change, `check:<which>`). Both recorded at open, and the closing receipt records the receipt number at which each became true. A bounded job needs both before any spec is applied (preflight refuses, naming the flag); with `outcome_known` false the first decision is "what does done look like", and `job close` writes `pending`, never `accepted`, with the reason.
- A bounded job whose close is refused is still closed: its folder moves to done with result `rejected` and the uncovered lines in the closing receipt, because a partial task must not pose as complete and the record must be terminal; a new revision redoes it.
- The operation vocabulary is declared once, in custodian_kit (`change::Operation`), because the preflight reads it and code_passenger implements it; code_passenger depends on the kit already, so the kit names the words and code_passenger's match over them is exhaustive (a word with no implementation does not compile).
- The change spec is one document for preflight and transform (1o modifier `change`, TOML twin), declared in custodian_kit with the other three; code_passenger reads it through the kit.
- Creation first (James, 11:1xZ): make_struct, make_enum, make_impl (inherent or a trait), add_fn (a function in an impl), make_fn (a free function), add_field, add_variant, add_derive, add_attribute, add_module, add_dependency (through code_passenger's `dep add`), add_test; then from the reading: add_constructor, add_method, add_trait_impl, change_signature, rename, move, and extract and gate. None of the reading's nine is dropped.
- A body is never free text the tool trusts: an operation's body is an expression (generated through simple_impl's `simple_method!` / `getter!` / `setter!` / `checked_method!` lines where the shape fits) or `todo!()` with the doc line; cargo check over the check matrix on a scratch copy is the postcondition of every operation, then a fresh klepto scan proves the facts.
- A decision asked is a task_history `problem` record (its id the digest of the question), a decision made is a `solution` record with the same id, the answer and the reason; the impact record is a `diagnosis` record. No new task_history record kind: the nine kinds hold all three.
- A decision answered anywhere in the project's task histories is answered: the same question (same digest) is never asked again, in any job.
- The task states proposed, ready, running, blocked, paused, verifying, completed, failed are one word set declared once in the kit, derived from the records (never stored as a second copy): proposed = a plan or a change spec with no preflight; ready = authorized by preflight; running = the job folder in running; blocked = an open decision; paused = queued with a checkpoint; verifying = verify lines not yet satisfied; completed = result accepted; failed = result failed_test or rejected.
- Bounded needs code-passenger installed (it is the writer); a bounded job start without it is refused.
- F1: the journal is rebuilt from the receipt files when it holds fewer receipts than `data/receipts/` has, inside the first open; a reading's row comes from its receipt's outputs (the page and record), found where the receipt says or in its job's folder.
- Item 8's crate list: James's 89 crates read from crates.io on 2026-10-19; the ones this increment uses are named in docs/COMPOSITION.md with what each covers.
